# LinkML schema and RDF route

`svv_vokabular.yaml` models template v8 (vokabular sheet; code lists excluded).
For every slot it records:

- `slot_uri`: the RDF property;
- `in_language`: the language tag;
- `annotations.excel_column` / `excel_name`: the v8 column letter and technical name from row 22, which is also intended as the SharePoint column name;
- `annotations.requirement`: obligatorisk / anbefalt / valgfri.

## Pipeline

```
v8 Excel ──reader──> LinkML data (YAML) ──linkml validate──> report
                          │
                          └──project RDF writer──> Turtle ──pySHACL (generated + fixed + cross-row shapes)──> report
```

```bash
./schema/generate.sh                                     # regenerate artefacts after editing the schema
.venv/bin/python -m vocabtool rdf out/N101-v8.xlsx --out out/rdf
```

## Generated artefacts (`generated/`)

| File | Use |
| --- | --- |
| `svv_vokabular.schema.json` | JSON Schema; output contract for LLM extraction (Pass A/B records) |
| `svv_vokabular_pydantic.py` | Pydantic classes; gate on LLM output in Python |
| `svv_vokabular.shacl.ttl` | SHACL as generated by LinkML (has the defects listed below) |
| `svv_vokabular.shacl.fixed.ttl` | SHACL used for validation: defects fixed, plus `shapes/cross_row.shacl.ttl` |
| `svv_vokabular.owl.ttl` | OWL of the *schema* (not the O0–O6 vocabulary-to-OWL conversion) |
| `docs/` | Markdown documentation per class, slot and enum |

## What standard LinkML (1.12.1) does not do, and how this project handles it

Each item below was tested here. None of it is assumed from documentation.

| Gap | Effect | Handling |
| --- | --- | --- |
| RDF dumper ignores `in_language` | `skos:prefLabel "bru"` without `@nb` | Project RDF writer `vocabtool/linkml_rdf.py` adds tags from the schema |
| RDF dumper writes enum text, not `meaning` | `euvoc:status "kandidat"` instead of the EU concept-status URI | RDF writer uses `meaning` |
| SHACL generator: several slots on one property each get `sh:maxCount 1` | a concept with `@nb` and `@nn` labels fails | Replaced by qualified shapes per language (`sh:qualifiedValueShape [sh:languageIn ("nb")]`) |
| SHACL generator sets `sh:datatype xsd:string` on language slots | every `"…"@nb` value fails | Replaced by `rdf:langString` + `sh:languageIn` |
| SHACL generator: container slot `concepts` | none; the RDF writer emits `skos:inScheme` instead | `rdf_skip` annotation |
| Cross-row rules (cycles, S27, Tier 1 isolated) | not expressible in LinkML | Hand-written SHACL-SPARQL in `shapes/cross_row.shacl.ttl` |

Negative test: a hand-made graph with duplicate nb labels, a German definition, a broader cycle,
a bad ID, a non-vegvesen e-mail, status as text and tier 7 was checked, and every one of these errors was reported.

## Open modelling questions

1. **exactMatch / closeMatch hold text, not IRIs** (N101: 228 values, e.g. `IFC4.3: IfcPavement`, `NS-EN 1317-7`).
   They are reported but not written to RDF. Options: real IRIs (the IFC 4.3 and CityGML classes have them,
   standards do not), or move the text to `skos:editorialNote` / `skos:note`.
2. **`dct:subject` contains `vok:N101` as text** in N101. The template allows "rdf:langString or skos:Concept",
   but one column cannot carry both cleanly. Decide on one.
3. **`dcat:contactPoint` as a plain e-mail string.** DCAT expects a `vcard:Kind` resource (e.g. `[ a vcard:Organization ; vcard:hasEmail <mailto:…> ]`).
   This is kept simple for now.
4. **Column AB `begrepseier`** has no property in row 21, so it is not modelled.
5. **`skosno` namespace:** the template uses `https://data.norge.no/vocabulary/skosno#`. The LinkML linter
   expects `http://data.norge.no/skosno#`. Check this against the current SKOS-AP-NO before publishing.
6. **`svv:tier` and `svv:kortnavn`** are project properties in a placeholder namespace (`http://example.org/vegvesen/vokabular/def#`), like the vocabulary URIs themselves.
